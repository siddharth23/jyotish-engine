## What this is

A sidereal (Vedic) astrological calculation engine: Dart FFI bindings and a WebAssembly build around
[Swiss Ephemeris](https://www.astro.com/swisseph/), plus a generic rule evaluator.

**Public repository, AGPL-3.0.** It is consumed by a separate private commercial product
(`../jyotish-platform`).

---

## Why this repository exists separately

Swiss Ephemeris is dual-licensed: a paid Professional licence (CHF 750), or **AGPL-3.0**. This
project uses the AGPL edition.

AGPL section 13 requires that users interacting with the software over a network be offered its
complete source. To use it in a commercial product without open-sourcing that product, the engine is
isolated here and executed **client-side only** — mobile via FFI, browser via WASM. No server-side
component links to or invokes it.

**That boundary is the entire reason this repository exists.** Read `docs/AGPL-BOUNDARY.md`.

Practical consequences for anything you write here:

- **Never add a server affordance.** No HTTP server, no daemon mode, no Node entry point, no hosted
  API client. CI rejects server framework dependencies.
- `loadEngine()` in the WASM package throws outside a browser. That guard is deliberate — keep it.
- Assume everything committed here is permanently public. No keys, no internal hostnames, no
  business rules.

## Scope — what belongs here and what does not

**Belongs:** astronomical and astrological *facts*. Positions, dignity, nakshatras, houses,
divisional charts, dashas, panchang, transits, and a generic evaluator for externally supplied rule
sets.

**Does not belong:** interpretation content, opinions about what a placement "means", product logic,
or anything specific to one application.

The rule evaluator returns **rule identifiers and the evidence that matched — never prose.** The
consuming application maps identifiers to text. This keeps content out of an AGPL package and lets
applications version their interpretations independently.

## Non-negotiables

**Determinism.** Identical inputs and identical engine version produce byte-identical output on
every platform. A chart delivered to a paying customer must be reproducible years later during a
dispute. No platform-dependent float formatting, no reliance on system time or locale, no unordered
collection serialisation.

**Versioning.** `engineVersion` is embedded in every result. Any change that can alter numerical
output **must** increment it. Consuming applications cache keyed on this value; a silent change makes
historical charts irreproducible.

**Cross-platform equality.** The Dart FFI and WASM builds must produce identical serialised output
for every test vector. This is stricter than the numerical tolerances and is checked separately.
Divergence means an astrologer's chart disagrees with the customer's — a correctness failure, not a
rounding difference.

**UTC only.** The engine accepts UTC. Local-to-UTC conversion is the caller's responsibility. Do not
add timezone handling here.

---

## Accuracy work

Any change affecting numerical output must:

1. State the reference source validated against — astro.com, JPL Horizons, or a named classical text.
   Be specific.
2. Add or update vectors in `test/vectors/reference_births.json`.
3. Keep FFI and WASM output identical.

**Expected values must be computed independently.** A vector generated by the code it tests proves
only that the code agrees with itself.

Tolerances: 1 arc-second on longitudes and cusps; 1 minute on dasha boundaries and sunrise/sunset.
Rule-based output (yogas, dignity, doshas) is compared exactly — there is no tolerance for a boolean.

The seven existing vectors guard the cases where astrology software silently fails: German double
summer time 1946, the 1950–79 DST gap, Calcutta's +05:53:20 pre-1955, the ambiguous DST fall-back
hour, high latitude (Tromsø), pre-1900 births, and ayanamsa comparison. All seven currently await
independent verification — `verifiedAgainst` is null. Filling those in is genuinely valuable work.

## Current state

The engine splits into two halves at `RawEphemeris`, and only one of them exists.

**Derivation half — implemented and tested in Dart.** Everything downstream of raw longitudes:
signs, nakshatras and padas, dignity, combustion, whole-sign and equal houses, the seven vargas,
the full Vimshottari tree, and tithi/yoga/karana. Pure arithmetic, no native code, 170 tests.
`assembleChart(BirthData, RawEphemeris)` is the entry point.

**Ephemeris half — not started.** Planetary longitudes, the ayanamsa value, the ascendant, quadrant
cusps, and sunrise/sunset all still have to come from Swiss Ephemeris. `fetch_swisseph.sh` and the
three build scripts are stubs with documented TODOs, so nothing can produce a real chart yet. The
`JyotishEngine` interface has no implementation: an FFI class will implement it by calling Swiss
Ephemeris to fill a `RawEphemeris` and handing that to the assembler.

**The WASM package is still empty.** The derivation half exists only in Dart. Cross-platform
equality is not merely unverified, it is currently impossible — the TypeScript side has nothing to
compare against. Porting the derivation layer, or compiling the Dart to JS, is an open decision.

The remaining first task is unchanged: get Swiss Ephemeris compiling for all targets and prove FFI
and WASM agree on the test vectors. All seven vectors still have `verifiedAgainst: null`.

Defaults: Lahiri (Chitrapaksha) ayanamsa, whole-sign houses, mean node. Vimshottari years are
365.25 days (`vimshottariYearDays`) — that constant defines every dasha boundary the engine emits.
